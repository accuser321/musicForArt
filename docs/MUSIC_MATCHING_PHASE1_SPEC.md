# 音乐匹配一期开发规格

## 1. 一期目标

一期只做一个明确能力：

`判断用户当前上传的音乐，是否适合当前作品`

这里的“作品”由三部分组成：
- 赛道
- 文本
- 演绎音频时间轴

一期不做：
- 音乐库推荐 1~3 首
- 音乐库后台完整管理
- 向量检索
- 大规模 Neo4j 推荐图

## 2. 用户端定位

建议将当前：

`2) 音乐分析（独立）`

逐步升级为：

`2) 判断这首音乐是否适合作品`

但为了兼容现有链路，一期可以先保持按钮位置不变，只升级结果页结构。

## 3. 一期输入前提

### 必需输入

- 项目赛道
- 文本
- 用户上传音乐

### 强推荐输入

- 演绎音频

说明：
- 没有演绎音频时，仍可做“赛道 + 文本”的适配判断；
- 有演绎音频时，再额外给出“节奏 / 对位可执行性”的判断。

## 4. 一期结果输出

建议结果页固定输出 6 个模块。

### 4.1 综合结论

字段：
- 综合结论：适合使用 / 可用但建议剪辑调整 / 不建议使用
- 综合评分：0~100
- 一句话总结

### 4.2 赛道匹配

字段：
- 赛道匹配度：高 / 中 / 低
- 当前音乐偏向赛道
- 是否与当前项目赛道一致
- 不一致原因

示例：
- 当前项目：科幻
- 当前音乐更偏：悬疑
- 原因：低频压迫持续时间长、节奏推进偏潜伏，缺少科幻所需的空间感和电子质感

### 4.3 文本匹配

字段：
- 情绪匹配度
- 文本情绪是否与音乐一致
- 场景变化是否能被音乐结构承接
- 关键不适配点

### 4.4 演绎匹配

仅在有演绎音频时展示。

字段：
- 节奏匹配度
- 对位可执行性
- 哪些语句段落适合进入音乐
- 哪些段落需要压低或退出

### 4.5 剪辑建议

字段：
- 建议保留段
- 建议淡入点
- 建议高潮点
- 建议淡出点
- 如果需要二次剪辑，建议如何裁切

### 4.6 更换建议

仅在“不建议使用”时重点展示。

字段：
- 建议更换原因
- 推荐寻找的音乐方向
- 可提示：
  - 更适合的情绪
  - 更适合的节奏
  - 更适合的风格关键词

## 5. 结果页文案风格要求

不要只展示技术结果：
- marker 数
- section 数
- bpm

这些可以保留在二级信息区，但主视图必须优先展示：
- 适合不适合
- 为什么
- 怎么剪
- 不适合应该换什么

## 6. 评分模型建议

一期建议采用“规则评分 + LLM 解释”的混合模式。

### 6.1 评分维度

- 赛道一致度：25
- 情绪一致度：25
- 节奏一致度：20
- 结构一致度：15
- 演绎可对位性：15

总分：
- 100 分

### 6.2 结论阈值建议

- 80~100：适合使用
- 60~79：可用但建议剪辑调整
- 0~59：不建议使用

### 6.3 为什么不用纯 LLM 打分

因为纯 LLM：
- 波动大
- 难复现
- 用户复测时不稳定

所以建议：
- 规则层负责基础分
- LLM 负责生成原因和建议

## 7. 一期后端接口设计

### 7.1 保留现有接口

保留：

`POST /api/analysis/<project_id>/music`

用于：
- 解析用户上传的单首音乐
- 生成基础音乐分析结果

### 7.2 新增接口

建议新增：

`POST /api/analysis/<project_id>/music-match`

#### 输入

无需额外 body，后端从项目现有分析结果中取：
- 当前项目 genre
- audio_analysis
- text_analysis
- narration_analysis（若存在）

#### 输出建议结构

```json
{
  "verdict": "可用但建议剪辑调整",
  "score": 74,
  "summary": "音乐情绪与文本大体一致，但节奏推进偏慢，高潮进入略晚。",
  "genre_match": {
    "score": 68,
    "verdict": "中等匹配",
    "current_genre": "科幻",
    "music_bias_genres": ["悬疑", "科幻"],
    "reasons": []
  },
  "text_match": {
    "score": 79,
    "verdict": "较匹配",
    "reasons": []
  },
  "narration_match": {
    "score": 72,
    "verdict": "可对位",
    "reasons": []
  },
  "editing_advice": {
    "intro_start_sec": 12.4,

  }

```

## 8. 一期数据表建议

### 8.1 新增表：music_match_result

建议字段：

- `id`
- `project_id`
- `audio_analysis_id`
- `text_analysis_id`
- `narration_analysis_id` nullable
- `genre_match_json`
- `text_match_json`
- `narration_match_json`
- `editing_advice_json`
- `replace_advice_json`
- `verdict`
- `score`
- `summary`
- `created_at`
- `updated_at`

作用：
- 存一期匹配结果
- 便于复测与复用
- 后续可做结果缓存

### 8.2 是否需要音乐素材库表

一期：
- 可以暂时不建完整候选音乐库表

二期：
- 再新增 `music_asset`

## 9. 一期服务层建议

建议新增服务文件：

- `backend/app/services/music_match.py`

职责：
- 汇总音频、文本、演绎结果
- 计算规则分
- 生成 LLM prompt 输入
- 输出最终匹配结论

### 9.1 服务输入

- 当前项目赛道
- 音乐分析结果
- 文本分析结果
- 文本演绎结果（可选）

### 9.2 服务输出

- 规则评分结果
- 结构化结论
- 用户可读摘要

## 10. Prompt 建议

建议新增 Prompt：

- `V1-music_match_task.txt`

任务不是重新做音乐解析，而是：
- 在已有音乐分析、文本分析、演绎时间轴基础上
- 判断适配关系
- 输出不适配原因
- 输出剪辑建议

### Prompt 要求重点

1. 不能空泛
不能只说“更合适”。

2. 必须说明不适合原因
如：
- 风格偏悬疑
- 情绪推进过慢
- 高潮进入点晚于文本情绪转折

3. 必须给出可执行建议
如：
- 进入点放在第 X 秒
- 第 Y 秒后建议淡出
- 当前音乐不适合，建议寻找“电子冷感 / 空间感 / 中速推进”方向

## 11. 前端页面建议

### 11.1 用户按钮阶段

一期最省改法：
- 仍保留 `2) 音乐分析`
- 分析完成后自动附带或增加一个：
  - `查看是否适合作品`

或者直接：
- `2) 音乐匹配`

### 11.2 结果区结构

建议顺序：

1. 综合结论
2. 赛道匹配
3. 文本匹配
4. 演绎匹配
5. 剪辑建议
6. 更换建议
7. 技术详情（折叠）

### 11.3 技术详情应折叠

如：
- BPM
- marker 数
- section 数
- 标签列表

不要抢主视图。

## 12. 管理后台一期最小支持

一期后台不需要立刻做音乐库大后台，但建议增加：

### 12.1 匹配记录查看

让运营能查看：
- 哪些项目音乐被判定不适合
- 最常见的不适合原因

### 12.2 常见赛道风格配置

建议做轻量配置：
- 每个赛道的建议音乐特征
- 每个赛道的禁忌风格

这可以先存 JSON，不必一开始就上 Neo4j。

## 13. Neo4j 一期是否要介入

我的建议：

一期不强依赖 Neo4j。

原因：
- 一期目标是“判断当前音乐是否适合作品”
- 用现有结构化结果 + 规则 + LLM 就能先做出来

Neo4j 更适合在二期介入：
- 建音乐标签关系图
- 建赛道-情绪-风格-叙事功能关系
- 给推荐做解释和加权

## 14. 一期开发顺序建议

### Step 1

新增：
- `music_match.py`
- `V1-music_match_task.txt`

### Step 2

新增：
- `POST /api/analysis/<project_id>/music-match`
- `music_match_result` 表

### Step 3

调整用户端：
- 升级音乐结果页
- 增加匹配结论与剪辑建议

### Step 4

后台增加最小查看能力：
- 查看音乐匹配结果摘要

## 15. 结论

一期完全可以在现有系统基础上落地，不需要等音乐库推荐体系全部建完。

最重要的是先让用户获得这类真实价值：

`我手里的这首音乐，到底适不适合这个作品？`

这一步一旦做出来，系统的感知价值会明显提升。
