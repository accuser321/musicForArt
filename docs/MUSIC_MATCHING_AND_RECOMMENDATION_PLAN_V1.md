# 音乐匹配与推荐方案 V1

## 1. 目标

当前“音乐分析”功能更偏向对单首音乐做结构解析，但用户真实诉求更接近下面两类：

1. 我手里已经有音乐  
   需要系统判断：
   - 这首音乐是否适合当前赛道
   - 是否适合当前文本
   - 是否适合当前演绎音频节奏
   - 如果适合，怎么剪
   - 如果不适合，为什么不适合

2. 我手里没有合适音乐  
   需要系统主动推荐：
   - 1~3 首更适合的音乐
   - 每首为什么适合
   - 适合落在哪些文本段落
   - 建议如何进入和退出

因此，建议将现有“音乐分析”能力升级为更完整的：

`音乐匹配与推荐`

## 2. 产品结构建议

### 2.1 用户端能力拆分

建议拆成两个主入口。

#### A. 我的音乐是否合适

输入：
- 赛道
- 文本
- 演绎音频
- 用户上传音乐

输出：
- 赛道匹配度
- 文本匹配度
- 演绎节奏匹配度
- 综合结论：适合 / 一般 / 不适合
- 不适合原因
- 若适合：剪辑建议、进入建议、高潮建议、退出建议

#### B. 帮我推荐更合适的音乐

输入：
- 赛道
- 文本
- 演绎音频（可选但强推荐）

输出：
- 推荐 1~3 首音乐
- 每首的推荐原因
- 每首适合的文字段落
- 每首建议进入点 / 高潮点 / 退出点

### 2.2 用户视角的重要变化

用户不再只看到“音乐解析结果”，而是看到：

- 是否适合我的作品
- 为什么适合 / 不适合
- 如果不适合，我该换什么类型
- 如果没有音乐，系统推荐什么

这更符合真实业务价值。

## 3. 一期优先做什么

建议先做一期，不要一步做到最重。

### 一期目标

先做：

`我的音乐是否合适`

原因：
- 当前系统已经有：
  - 音乐分析
  - 文本分析
  - 文本演绎分析
  - 文本音乐执行单
- 这些能力已经足够支撑“匹配判断 + 剪辑建议”
- 不需要先建立很大的音乐库，就能给用户实用价值

### 一期不强做

暂缓完整上线：

`帮我推荐更合适的音乐`

因为这一步依赖：
- 音乐候选库
- 已分析音乐的持久化
- 推荐排序
- 推荐理由生成

这更适合作为二期。

## 4. 功能判断逻辑

### 4.1 适合与否，不只是看赛道标签

音乐匹配不能只看：

`文本是科幻 -> 音乐也标科幻`

还要综合：
- 情绪是否一致
- 能量递进是否一致
- 结构转折是否能接住文本节奏
- 音乐锚点是否能服务演绎时间轴

### 4.2 建议输出的判断维度

建议输出以下维度：

1. 赛道匹配
2. 情绪匹配
3. 节奏匹配
4. 结构匹配
5. 演绎对位可执行性
6. 综合建议

### 4.3 适合结论建议分层

- `适合使用`
- `可用但建议剪辑调整`
- `不建议使用`

这样比简单的“适合/不适合”更符合业务。

## 5. 二期：音乐推荐能力

### 5.1 二期目标

在系统中建立“已分析音乐库”，并支持按作品需求做推荐。

### 5.2 推荐结果建议

每次给：
- Top 1
- Top 2
- Top 3

每首都要给：
- 推荐理由
- 适合赛道
- 适合情绪
- 适合的文本段落
- 进入建议
- 风险提醒

### 5.3 推荐排序建议

建议综合评分：

- 赛道一致度
- 情绪一致度
- BPM/节奏一致度
- 乐段结构一致度
- 锚点可对位能力
- 历史人工确认加权

## 6. 数据设计建议

不建议把所有内容都只放在 Neo4j。

更稳的方案是：

### 6.1 关系库 / JSON 持久化

用于存：
- 音乐文件基础信息
- 音乐分析结果 JSON
- section / marker / bpm / tags
- 推荐结果缓存

适合放在现有业务库里。

建议新增：

- `music_asset`
- `music_analysis_cache`
- `music_match_result`
- `music_recommendation_result`

### 6.2 Neo4j

用于存：
- 赛道
- 情绪
- 音乐风格标签
- 叙事功能
- 配器倾向
- 适配关系
- 不适配关系

更适合做：
- 关系推理
- 规则加权
- 推荐解释

### 6.3 相似召回层

用于未来扩展：
- 向量检索
- 特征相似度检索

例如：
- 文本需求向量
- 音乐风格向量
- 情绪向量

这层适合在二期再接。

## 7. 为什么 Neo4j 适合，但不应独占

Neo4j 很适合表达：

- 科幻 -> 冷感 / 空间感 / 电子质感
- 悬疑 -> 压迫 / 潜伏 / tension
- 言情 -> 抒情 / 细腻 / 渐进
- 玄幻 -> 苍茫 / 灵动 / 神秘 / 冲突升级

也适合表达：

- 某种情绪常对应哪些音乐标签
- 某种叙事转折常需要哪些锚点结构
- 哪些音乐标签与哪些赛道明显不适配

但不适合让它承担全部原始分析结果存储。

原因：
- section / marker / bpm / 文件信息这类结构化结果，更适合关系库/JSON
- 后续检索、缓存、导出也更方便

因此建议：

`Neo4j 负责关系能力`

`关系库负责结果落库`

## 8. 一期接口建议

### 8.1 现有音乐分析保留

保留：

`POST /api/analysis/<project_id>/music`

用途：
- 单首音乐结构分析

### 8.2 新增音乐匹配接口

建议新增：

`POST /api/analysis/<project_id>/music-match`

输入：
- 当前项目文本分析结果
- 音乐分析结果
- 演绎时间轴

输出：
- 匹配评分
- 赛道匹配结论
- 文本匹配结论
- 不适配原因
- 剪辑建议

### 8.3 二期新增音乐推荐接口

建议新增：

`POST /api/analysis/<project_id>/music-recommend`

输入：
- 赛道
- 文本分析结果
- 演绎时间轴

输出：
- top 1~3 推荐音乐
- 推荐理由
- 对位建议

## 9. 用户端页面建议

### 9.1 调整“音乐分析”模块

建议把用户端当前“音乐分析”模块拆成：

- `2) 分析我的音乐`
- `2.5) 推荐更合适的音乐`

如果一期暂不做推荐入口，可以先只做：

- `2) 判断这首音乐是否适合作品`

### 9.2 音乐匹配结果页建议

建议用户看到：

- 综合结论
- 是否适合当前赛道
- 是否适合当前文本
- 是否适合当前演绎节奏
- 关键原因
- 剪辑建议

而不是只看技术性 section、marker。

### 9.3 推荐页建议

用户看到：

- 推荐音乐 1~3 首
- 每首推荐原因
- 每首适合哪一段文本
- 每首建议怎么进入

## 10. 管理后台建议

后台需要增加：

### 10.1 音乐库管理

- 上传音乐
- 查看音乐分析结果
- 修改音乐标签
- 标记赛道适配

### 10.2 音乐推荐关系维护

- 赛道 -> 风格标签
- 情绪 -> 音乐标签
- 不适配关系
- 推荐权重

### 10.3 推荐效果反馈

- 用户最终是否采用推荐音乐
- 哪首推荐音乐被下载/使用最多
- 哪些文本场景推荐不准

这会帮助后续推荐越来越准。

## 11. 技术风险与建议

### 风险 1：仅靠 LLM 做推荐不稳定

建议：
- LLM 负责解释和建议
- 不负责单独决定最终匹配

### 风险 2：只有赛道标签不够

建议：
- 一定要叠加情绪、节奏、结构

### 风险 3：音乐库扩大后检索会慢

建议：
- 一期先少量库
- 二期再做向量召回或特征索引

### 风险 4：推荐理由容易空泛

建议：
- 推荐理由必须锚定文本、音乐、演绎三个维度
- 不允许只说“更适合”

## 12. 推荐实施顺序

### 阶段一

完成：
- “我的音乐是否合适”
- 输出适配原因和剪辑建议

### 阶段二

完成：
- 音乐候选库
- Top 1~3 推荐
- 推荐原因

### 阶段三

完成：
- Neo4j 推荐关系增强
- 推荐反馈回流
- 精准度持续优化

## 13. 最终建议

建议这次不要把它继续叫做单纯的“音乐分析”。

更合适的产品表达是：

- `音乐匹配`
- `音乐匹配与推荐`

如果只做一期：

`音乐是否适合作品`

如果二期也做：

`音乐匹配与推荐`

这会比当前命名更贴合用户真实诉求。
