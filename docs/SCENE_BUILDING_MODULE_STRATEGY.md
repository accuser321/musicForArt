# 场景搭建模块策略文档

版本：v0.1  
更新时间：2026-03-19  
状态：框架确认，待进入提示词提炼与开发阶段

## 1. 文档目的

这份文档用于沉淀“场景搭建模块”的大框架思路，确保后续开发不是零散加功能，而是在统一目标下推进。

这份文档不是最终 PRD，但应作为后续产品、提示词设计、图谱设计、代码开发的方向基线。

## 2. 模块定位

场景搭建是系统的另一个核心模块，其重要性与动作分析相同。

系统后续明确分为两个并列核心模块：

1. 动作分析
2. 场景搭建

动作分析解决：

1. 文本里人物做了什么
2. 需要哪些动作音效

场景搭建解决：

1. 文本里当前是什么场景
2. 场景由哪些可听见的元素构成
3. 应命中哪些场景音效
4. 哪些素材可直接下载
5. 哪些音效仍有缺口

## 3. 模块边界

### 当前阶段明确要做

1. 文本场景识别
2. 场景构成拆解
3. 场景图谱命中
4. 场景音效召回
5. 场景音效下载
6. 场景缺口补充链路

### 当前阶段明确不做

1. 导演思维分析
2. 镜头语言分析
3. 近景 / 中景 / 远景设计
4. 混响、延迟、空间声场创作建议
5. 替代创作者做主观艺术决策

说明：

这些能力不属于“场景搭建模块”的第一阶段，而应放到后续第三阶段：

1. 动作分析模块稳定
2. 场景搭建模块稳定
3. 再做第三模块：导演思维融合

## 4. 系统主链路

场景搭建建议沿用当前动作分析的主架构：

1. 用户上传文本
2. LLM 输出场景分析结论
3. 系统基于结论命中场景图谱 / Neo4j
4. 命中场景关联词
5. 命中场景音效
6. 输出可下载结果
7. 对缺口生成补充链路

这意味着：

1. LLM 负责先得出结论
2. 图谱与 Neo4j 负责做结构化命中与复用
3. 素材层负责下载与缺口补齐

## 4.1 上线前的基础种子策略

场景搭建模块不应该在上线时依赖“完全空图谱 + 等用户文本慢慢喂养”。

更合理的上线方式是：

1. 先预置一版高复用的基础场景图谱
2. 先围绕这些基础场景补齐一批基础素材
3. 再由真实用户文本、补充单与运营维护持续增长

这样做的原因：

1. 场景搭建比动作分析更强调“可复制性”
2. 大量文本虽然写法不同，但会落到相似的大场景
3. 如果一开始图谱完全为空，场景模块会过度依赖保底结果，影响可解释性与稳定性

第一批预置种子应以：

1. 通用场景节点
2. 通用场景模板
3. 少量赛道样板场景

为主，而不是一开始就堆很多重赛道特化节点。

当前已经按这个原则启动第一批种子扩充：

1. 通用场景：
   - 教室
   - 操场
   - 海边
   - 街道
   - 雨夜街巷
   - 房间
   - 卧室
   - 走廊
   - 客栈
   - 市集
   - 山林
   - 河边
2. 赛道样板场景：
   - 玄幻：山林夜路、宗门大殿
   - 言情：闺阁深夜
   - 悬疑：废弃走廊
   - 科幻：舰桥

这意味着，场景搭建模块的增长模式应理解为：

1. 先有基础种子库
2. 再由真实文本不断命中、校正和扩展
3. 再由运营把高频结果沉淀为更稳定的大场景集合

## 6. 最重要的设计原则：场景搭建的可复制性

这是场景搭建模块区别于动作分析模块的关键原则。

### 6.1 为什么场景更强调可复制性

原因：

1. 场景文本表达会变化
2. 但声音制作上，很多文本最终会收敛到相似的大场景
3. 场景天然适合沉淀成模板和可复用集合

例如很多不同文本，最后都可能对应到：

1. 深夜山林
2. 雨夜街巷
3. 客栈大堂
4. 宫廷长廊
5. 集市白昼

因此，场景搭建模块必须形成：

1. 大场景集合
2. 稳定的场景构成词库
3. 稳定的场景音效池

### 6.2 这带来的系统价值

1. 用户结果更稳定
2. 同类文本会更容易命中同类场景
3. 音效素材复用率更高
4. 运营维护成本更低
5. 系统可逐步沉淀为“场景音效库”

### 6.3 设计结论

新文本分析时应优先：

1. 命中已有场景集合
2. 复用已有场景音效池

而不是每次从零生成一个新场景。

只有明显不属于现有集合时，才生成新的场景候选。

## 7. 图谱层建议

场景搭建图谱建议至少包含五层对象：

1. 场景主节点
2. 场景构成词
3. 直达场景音效
4. 组合场景音效
5. 场景模板 / 场景集合

### 7.1 场景主节点

例如：

1. `通用::夜林`
2. `玄幻::山林夜路`
3. `言情::闺阁深夜`
4. `悬疑::废弃走廊`

### 7.2 场景构成词

例如：

1. 夜风
2. 树影
3. 虫鸣
4. 湿地
5. 远山

### 7.3 直达场景音效

例如：

1. 风声
2. 叶响
3. 虫鸣
4. 雨滴
5. 木门轻响

### 7.4 组合场景音效

例如：

1. 夜林氛围
2. 雨夜街巷氛围
3. 庙堂人群氛围

### 7.5 场景模板 / 场景集合

例如：

1. 夜林类
2. 客栈类
3. 宫廷类
4. 战场类
5. 雨夜街巷类

说明：

“场景模板 / 场景集合”层是场景模块复用性的核心，不可缺失。

## 8. 通用场景与赛道场景

和动作图谱一样，场景搭建后续也应逐步形成：

1. 通用场景集合
2. 赛道场景集合

### 通用场景

指跨赛道都能成立的场景基础结构。

例如：

1. 夜林
2. 雨夜街巷
3. 客栈大堂

### 赛道场景

指带有赛道特化风格的场景表达。

例如：

1. 玄幻山林夜路
2. 言情闺阁夜谈
3. 悬疑废弃医院走廊

## 9. 与动作分析的关系

动作分析和场景搭建在当前阶段：

1. 并列
2. 不混模块
3. 不共用一个结果区

未来当两个模块都稳定后，再在结果页增加“联动区”，并进一步进入第三模块：

1. 导演思维融合
2. 动作与场景统一调度
3. 创作层建议

## 10. 提示词来源

场景搭建模块的提示词，后续应以用户提供的“有声书老师教学逐字稿”为基础材料。

开发原则：

1. 不凭空拍脑袋写提示词
2. 从老师逐字稿中提炼结构化规则
3. 抽取可稳定复用的分析维度
4. 再反向设计场景识别提示词

后续要提炼的内容包括：

1. 场景识别提示词
2. 场景构成拆解提示词
3. 输出字段格式
4. 命中图谱所需的结构化字段

## 11. 后续建议开发顺序

建议顺序：

1. 先确定场景搭建模块的数据结构
2. 再提炼老师逐字稿形成提示词
3. 再设计 Neo4j 图谱结构
4. 再开发用户端第一版
5. 再补运营端场景维护链路

不建议直接跳过结构设计开始写功能。

## 12. 当前结论

场景搭建不是动作分析的附加小功能，而是系统第二条核心主链路。

其价值不只在“分析文本”，更在于逐步沉淀出：

1. 高复用的大场景集合
2. 稳定的场景构成词库
3. 稳定的场景音效池

这是未来系统形成行业壁垒的重要方向。
